# ECG 平台深度面试复盘提示词设计

> 日期：2026-07-13  
> 状态：待用户审阅  
> 目标：基于当前仓库事实，设计一套能够逼迫候选人讲清项目设计、实现、异常与测试的面试复盘提示词。

## 1. 目标与使用方式

这套材料不是项目生成提示词，也不是标准答案背诵稿。它用于以下复盘循环：

1. 候选人把单条提示词交给 AI 面试官，或自行限时作答。
2. 回答必须给出业务动机、数据流、状态变化、代码落点、异常路径和验证方法。
3. AI 面试官根据遗漏项继续追问，不因出现技术名词就判定通过。
4. 回答最后必须区分当前实现、演示边界和企业化演进，避免把规划说成已完成。

最终题库规模控制在 30～40 条，适合拆成多轮训练，不追求一次覆盖仓库全部文件。

## 2. 事实基线

题库以当前 `main` 分支代码为事实来源，并优先引用以下实现边界：

- React 18、TypeScript、Redux Toolkit、Ant Design、Fabric.js、TensorFlow.js。
- Webpack 构建与 `React.lazy()` 页面级路由，不把本仓库说成 Vite 构建。
- 病例链路由浏览器、`clinicApi` 与 Node mock API 构成；网络错误可回退，HTTP 错误不静默降级。
- ECG 数据通过 JSON、HL7、DICOM、WFDB 等入口归一为 `ECGRecord`、`ECGLead` 和 `Annotation` 合同。
- Annotation Studio 负责编排导入、记录切换、标注、播放、自动 R 峰、AI 分析、保存和导出。
- TF.js 模型加载具有真实模型、IndexedDB 缓存、显式 mock 和失败不可用等状态边界。
- Firebase 保存采用延迟初始化与 debounce；记录切换必须防止旧标注写入新记录。
- FastAPI sidecar 提供训练 REST/SSE、checkpoint、助手与 Minimax 代理能力，并读取 ECGFounder 文件状态。
- 项目是 research preview；mock 数据、轻量 parser、缺少完整真实模型验收和生产身份审计必须主动说明。

若历史设计文档与当前源码冲突，以当前源码、测试和最新审计结论为准。

## 3. 题库总体结构

### 3.1 开场与全局架构：3 条

- 60 秒项目介绍：只允许讲一条主链和两个最难问题。
- 3 分钟架构展开：浏览器、领域服务、状态层、外部边界。
- 架构图反向解释：从导出结果倒推到原始输入与来源标记。

### 3.2 八条核心流程：每条 2～3 题

1. 病例加载与离线回退。
2. 多格式 ECG 导入与统一数据合同。
3. 信号预处理、质量评估与特征提取。
4. Fabric.js 波形渲染与人工/自动标注。
5. Redux 状态边界与记录切换清理。
6. TF.js 模型加载、推理、热力图与显式 mock 降级。
7. Firebase 持久化、debounce 竞态与 JSON/CSV 导出追溯。
8. ECGFounder sidecar、训练 REST/SSE、助手与安全边界。

### 3.3 专项压力题：8～10 条

- 为什么网络不可达可以 fallback，而 HTTP 500 不能。
- 为什么 TF Tensor、Worker 和 Fabric Canvas 不应进入 Redux。
- A 记录切换到 B 记录时，哪些状态必须同时失效。
- 缓存写失败为什么不能使本次已加载模型失效。
- softmax 与 sigmoid 输出合同为什么不能共用同一种归一化。
- SSE 相比轮询和 WebSocket 的选择依据及断流处理。
- Sidecar admin token、路径 containment 与 checkpoint 文件名校验。
- Minimax API key 为什么只能留在 sidecar。
- 如何把一次演示 bad case 固化为确定性回归测试。

### 3.4 反事实与演进题：5～7 条

- 如果把浏览器 parser 移到后端，接口和测试怎样变化。
- 如果病例从 20 条 mock 扩展到百万级，现有边界先在哪里失效。
- 如果支持多人协同标注，Redux、Firebase 和冲突解决如何演进。
- 如果训练从单机共享文件迁到任务队列，状态模型和事件流如何重构。
- 如果要宣称临床可用，还缺哪些模型、合规、安全和数据验证门槛。

## 4. 单题的“六层拷打”模板

每条核心题都使用同一组评分维度，但追问内容必须贴合具体流程：

1. **需求层**：用户问题是什么，为什么这个流程存在。
2. **合同层**：输入、输出、关键类型、状态机和不变量是什么。
3. **实现层**：哪些组件、服务、slice、hook 或端点共同完成；调用顺序是什么。
4. **异常层**：失败如何分类，哪些能降级，哪些必须 fail-closed，用户看到什么。
5. **验证层**：最小单元、合同、集成或 E2E 用例如何设计，关键断言是什么。
6. **权衡层**：为何选择当前方案，它在规模、安全、性能或可维护性上的代价是什么。

通用提示词骨架：

> 不看文档，完整解释【流程】。先说明用户目标，再给出从输入到输出的逐步数据流。回答必须指出当前仓库中的关键类型、状态和实现位置，并解释至少两个异常分支、一个竞态或一致性风险、对应测试断言以及当前方案的取舍。最后把内容分成“当前已实现”“演示边界”“下一步演进”。禁止只罗列技术栈。

## 5. 三种题型

### 5.1 白板讲解题

要求候选人从零组织链路。提示词不给文件名，只给业务场景，检验是否建立了自己的系统模型。

### 5.2 故障注入题

提供一个具体故障，例如“真实模型加载成功但 IndexedDB 保存失败”或“Firebase debounce 期间 URL 从 A 切到 B”，要求预测现象、定位责任边界并设计回归测试。

### 5.3 反方质询题

先给出一个看似合理但有问题的方案，例如“所有请求失败都返回 mock 数据”，要求候选人指出它破坏的合同、风险和替代方案。

三种题型应交错出现，避免题库退化为固定问答背诵。

## 6. 单题输出格式

最终每条题目包含四部分：

1. **主提示词**：可直接复制给 AI 面试官。
2. **继续追问条件**：回答遗漏哪些事实时必须追问。
3. **合格回答锚点**：只列必须覆盖的事实，不提供可机械背诵的完整答案。
4. **危险回答**：列出夸大、混淆或只报技术名词的典型错误。

示例：

> **主提示词**：用户上传同名 `.hea` 与 `.dat` 后，数据如何成为画布可消费的 `ECGLead[]`？请解释配对时机、采样率与导联合同、解析失败展示、旧记录状态清理和最小测试矩阵。
>
> **继续追问条件**：若回答没有解释单独 `.dat`、不同导联长度或重新导入时旧推理结果如何处理，继续追问。
>
> **合格回答锚点**：WFDB 成对输入；统一 lead 合同；解析错误可解释；新导入使 annotations 与 inferenceResults 失效；至少包含正常、缺文件、损坏文件和状态泄漏测试。
>
> **危险回答**：声称 parser 已达到完整临床 WFDB 兼容；只说“调用后端解析”；忽略旧状态。

## 7. 面试官执行协议

题库开头附一段可直接使用的 AI 面试官系统提示词：

- 每次只问一题，根据回答动态追问。
- 不主动泄露合格回答锚点。
- 候选人说出技术名词后，继续追问数据合同和失败路径。
- 候选人声称“已实现”时，要求给出代码位置、状态变化或测试证据。
- 候选人混淆当前实现与未来方案时，立即要求重新分类。
- 每题按六层各 0～2 分评分，总分 12 分；低于 8 分必须重答。
- 一轮结束只总结三个最薄弱的知识缺口，并生成下一轮定向题。

## 8. 难度梯度

- **第一轮：能讲通**。重点是主链、类型和组件关系。
- **第二轮：能讲深**。加入失败分类、竞态、资源生命周期和测试断言。
- **第三轮：能反驳**。要求比较替代方案并指出错误设计破坏的不变量。
- **第四轮：能演进**。在不篡改当前事实的前提下完成生产化设计。

同一流程可在不同轮次复用，但提示角度必须改变，不能只是换一种措辞。

## 9. 质量门槛

完整题库必须满足：

- 每个核心流程至少有一条白板题和一条故障/反方题。
- 每条题都能映射到当前仓库的具体代码、类型、测试或明确缺口。
- 至少 30% 的题目检查异常与一致性，而非 happy path。
- 至少 20% 的题目检查测试策略和关键断言。
- 所有 AI、parser、数据和安全能力都区分当前实现与生产要求。
- 不使用无法从仓库验证的性能数字、合规结论或模型准确率。
- 不把 `mock-api`、demo leads、mock inference 或本地助手包装成真实临床能力。
- 候选人完成题库后，应能独立讲清一条完整主链、三个关键风险和一套分层测试策略。

## 10. 最终交付物

设计获批后，完整材料输出为一份 Markdown 复盘手册，包含：

1. 使用说明与 AI 面试官系统提示词。
2. 60 秒与 3 分钟开场提示词。
3. 八条核心流程题库。
4. 专项压力题与反事实题。
5. 每题的追问条件、回答锚点和危险回答。
6. 一张自评分表和三轮复盘建议。
